## The real difference is how you pay

Both give you a database, auth, file storage and server functions. The choice usually comes down to two things: the shape of your data and how your bill grows.

Supabase is a Postgres database with tools around it. Its paid plan is a flat monthly fee, plus compute for each project. Firebase's main database is Firestore, a NoSQL document store. On the paid Blaze plan you pay for each document read, write and delete above the free quota. Budget alerts in Google Cloud only send emails. They don't stop Firestore from billing you.

## Supabase gives you Postgres and a fixed base price

<ToolFacts tool="Supabase" price="Free; Pro $25/mo per organization + compute" runsOn="Cloud or self-hosted (Docker)" license="Open source (Apache 2.0)" />

You write SQL, use foreign keys and joins, and can add Postgres extensions. The Free plan gives you 500 MB of database, 50,000 monthly active users and two active projects. Free projects pause after one week without activity, so a side project can go offline until you restore it.

Pro costs $25 a month per organization. It includes 8 GB of disk per project, 100,000 monthly active users and $10 of compute credits, enough for one Micro instance. Bigger instances cost more. Pro has a spend cap on by default, but the cap doesn't cover compute hours.

The whole stack is open source, and Supabase documents how to run it yourself with Docker Compose.

## Firebase charges for what you use

<ToolFacts tool="Firebase" price="Free Spark plan; Blaze pay-as-you-go" runsOn="Google Cloud" license="Proprietary" />

Firestore's free quota is 1 GiB of stored data, 50,000 document reads, 20,000 writes and 20,000 deletes per day. It resets every day around midnight Pacific time. Past that, you move to Blaze and pay per operation. Blaze keeps the same free quota, so a small app can still cost nothing.

The risk is an inefficient query or a loop that reads the same documents again and again. Firebase now offers spend caps that pause a service when it goes over budget, but only for Cloud Functions, App Hosting, AI Logic and Extensions. Firestore isn't on that list.

If you want SQL inside Firebase, SQL Connect runs on Cloud SQL for PostgreSQL. It has a 90-day no-cost trial. After that, Cloud SQL is billed separately.

## The same query in both

Here's how you get a user's ten latest orders. In Supabase you query a table:

```js
const { data, error } = await supabase
  .from('orders')
  .select('id, total, created_at')
  .eq('user_id', userId)
  .order('created_at', { ascending: false })
  .limit(10);
```

In Firestore you query a collection. Combining a filter and a sort on different fields needs a composite index, and every document returned counts as one read:

```js
import { collection, query, where, orderBy, limit, getDocs } from 'firebase/firestore';

const q = query(
  collection(db, 'orders'),
  where('userId', '==', userId),
  orderBy('createdAt', 'desc'),
  limit(10),
);
const snapshot = await getDocs(q);
```

On Supabase you aren't billed per row: you pay for the instance the query runs on. On Firestore it costs 10 reads each time it runs, so a page that runs it 5,000 times a day uses the whole free daily quota of 50,000 reads.

## What I set up first in client projects

I've shipped client projects on Supabase and on Firebase. I also host static sites like Musa Rosa on Firebase Hosting: a Next.js static export plus `firebase deploy --only hosting`. The mistake I see most often is the same on both platforms: a database exposed to the internet without access rules, because "we'll add security later".

On Supabase, I turn on Row Level Security for every table before writing the first query, and add one policy per action:

```sql
alter table orders enable row level security;

create policy "Users read their own orders"
on orders for select
to authenticated
using ( (select auth.uid()) = user_id );
```

On Firebase, test mode is fine for one afternoon and never for production. Write Firestore security rules that match how the app reads data:

```js
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /orders/{orderId} {
      allow read: if request.auth != null && request.auth.uid == resource.data.userId;
    }
  }
}
```

My rule of thumb for clients: if the data has relations and the budget must be predictable, Supabase. If the app is mostly documents, real-time and mobile, and the team wants Google to run everything, Firebase, with budget alerts set up on day one.

## How to choose in 30 seconds

- **Relational data and SQL:** Supabase.
- **You may want to self-host later:** Supabase.
- **Documents, real-time sync and zero servers:** Firebase.
- **A tiny app that must never pause:** Firebase.

## FAQ

### Is Supabase free?

Yes, with limits: 500 MB of database, 50,000 monthly active users and two active projects. Free projects pause after one week of inactivity.

### Can I host Firebase on my own servers?

No. Firebase is a proprietary Google service. Supabase publishes its full stack as open source and documents self-hosting with Docker.

### Can I set a spending limit on Firebase?

Partly. Budget alerts only send emails. Spend caps that pause a service exist for Cloud Functions, App Hosting, AI Logic and Extensions, but not for Firestore.
