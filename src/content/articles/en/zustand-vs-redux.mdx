## Modern Redux means Redux Toolkit

Comparisons often pit Zustand against old-style Redux, with switch statements and hand-written action types. That isn't how Redux is written anymore. Redux Toolkit is the official way to use Redux. `configureStore` sets up good defaults and DevTools, and `createSlice` generates actions and lets you write "mutating" updates safely through Immer.

So the real comparison is Zustand against Redux Toolkit. Both are actively maintained, MIT licensed and widely used. Zustand alone sees about 55 million npm downloads a week.

## The same counter in both

**Zustand.** The store is a hook. There's no provider to add:

```ts
import { create } from 'zustand';

type CounterState = {
  count: number;
  increment: () => void;
};

export const useCounter = create<CounterState>()((set) => ({
  count: 0,
  increment: () => set((state) => ({ count: state.count + 1 })),
}));

// In any component:
const count = useCounter((state) => state.count);
const increment = useCounter((state) => state.increment);
```

**Redux Toolkit.** A slice, a store and a provider at the root:

```ts
import { configureStore, createSlice } from '@reduxjs/toolkit';

const counterSlice = createSlice({
  name: 'counter',
  initialState: { count: 0 },
  reducers: {
    increment: (state) => {
      state.count += 1; // Immer turns this into an immutable update
    },
  },
});

export const { increment } = counterSlice.actions;
export const store = configureStore({ reducer: { counter: counterSlice.reducer } });

// Wrap the app once: <Provider store={store}><App /></Provider>
// In a component:
const count = useSelector((state: RootState) => state.counter.count);
const dispatch = useDispatch();
dispatch(increment());
```

Redux Toolkit has more pieces: slice, store, provider, `useSelector`, `useDispatch`. Each one has a fixed place, though, and that's the point for a big team.

## Zustand is a store in a few lines

<ToolFacts tool="Zustand" price="Free" runsOn="React, or plain JS with zustand/vanilla" license="Open source (MIT)" />

You create a store with one `create` call and get a hook back. Components select only the slice of state they need, so they re-render only when it changes. There's no provider, so the store also works outside components. For non-React code, `createStore` from `zustand/vanilla` gives you a store without the hook.

Zustand doesn't impose structure. That's great for small and medium apps, but on a large team you'll want your own conventions for splitting stores. For server data, most teams pair it with a separate data-fetching library rather than storing API responses by hand.

## Redux Toolkit gives a team one pattern

<ToolFacts tool="Redux Toolkit" price="Free" runsOn="React (via React-Redux), or plain JS" license="Open source (MIT)" />

Redux Toolkit 2.0 shipped alongside Redux 5 and React-Redux 9, and tightened the API by removing deprecated syntax. Every feature follows the same shape: a slice with state and reducers, actions dispatched from components. Developers who join a Redux codebase know where everything lives.

RTK Query is its biggest extra. You define API endpoints and it generates the hooks, caching, loading states and cache invalidation for you. That replaces a lot of hand-written fetching code. The Redux DevTools extension shows every action and state change and lets you step back through them.

## How I split state in React apps

The pattern I recommend on most projects: server data goes in a data-fetching library, and only real UI state goes in a store. Things like the open modal, the selected filters or the current step of a form. Once you do that, the store gets small, and Zustand is usually all you need.

One Zustand habit worth knowing: when a component reads several values, wrap the selector with `useShallow`, so it only re-renders when those values actually change:

```ts
import { useShallow } from 'zustand/react/shallow';

const { count, increment } = useCounter(
  useShallow((state) => ({ count: state.count, increment: state.increment })),
);
```

I'd pick Redux Toolkit when a large team needs every feature written the same way, or when RTK Query can replace a pile of hand-written fetching code. Those are good reasons. "Everyone uses Redux" isn't one anymore.

- **Most apps, least code:** Zustand.

- **A large team that needs one pattern:** Redux Toolkit.
- **Server data caching in the same tool:** Redux Toolkit with RTK Query.

## FAQ

### Is Redux dead?

No. Redux Toolkit is the official, actively maintained way to write Redux. What faded is the old hand-written style with switch statements and action-type constants.

### Does Zustand need a Provider?

No. `create` returns a hook you use in any component, with no provider around your app.

### Can Zustand use Redux DevTools?

Yes. Wrap your store with Zustand's `devtools` middleware and it shows up in the Redux DevTools extension.
