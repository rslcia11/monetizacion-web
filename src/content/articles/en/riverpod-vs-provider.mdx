## One author, two designs

Remi Rousselet wrote both. Provider wraps Flutter's `InheritedWidget`, so state lives in the widget tree and you read it through `BuildContext`. Riverpod's docs describe it as a rewrite of Provider, made to fix problems that couldn't be fixed inside Provider's design.

The best-known problem is `ProviderNotFoundException`. With Provider, if you read a provider from a widget that isn't below it in the tree, the app compiles but fails at runtime. That's easy to cause during a refactor. In Riverpod, providers are global objects, so that exception can't happen.

## The same counter in both

With **Provider**, you put a `ChangeNotifier` in the tree and read it through `context`:

```dart
class Counter extends ChangeNotifier {
  int value = 0;

  void increment() {
    value++;
    notifyListeners();
  }
}

void main() => runApp(
  ChangeNotifierProvider(create: (_) => Counter(), child: const MyApp()),
);

// Inside a widget's build method:
final count = context.watch<Counter>().value;
context.read<Counter>().increment();
```

With **Riverpod 3** and code generation, you declare a notifier class and read it through `ref`:

```dart
part 'counter.g.dart';

@riverpod
class Counter extends _$Counter {
  @override
  int build() => 0;

  void increment() => state++;
}

void main() => runApp(const ProviderScope(child: MyApp()));

class CounterText extends ConsumerWidget {
  const CounterText({super.key});

  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final count = ref.watch(counterProvider);
    return Text('$count');
  }
}

// Anywhere you have a ref:
ref.read(counterProvider.notifier).increment();
```

Riverpod has a few more concepts: `ProviderScope`, `ConsumerWidget`, `ref` and the generated `counterProvider`. In return, `counterProvider` is available everywhere with no tree position to get wrong. Code generation is optional, and you can declare providers by hand.

## Riverpod fixes Provider's weak spots

<ToolFacts tool="Riverpod" price="Free" runsOn="Flutter and plain Dart" license="Open source (MIT)" />

Because providers aren't widgets, you can read them in tests, background code or plain Dart with no UI. Async data gets an `AsyncValue` with loading, data and error states, so a screen that fetches from an API handles all three cases without extra flags.

Riverpod 3.0, stable since September 2025, simplified the API. The separate AutoDispose interfaces were merged into the regular ones. Failing providers now retry automatically with exponential backoff, and `Ref.mounted` tells you whether a provider is still alive. Offline persistence and mutations arrived as experimental features.

## Provider is simple and still fine

<ToolFacts tool="Provider" price="Free" runsOn="Flutter" license="Open source (MIT)" />

Provider is easy to pick up because it is Flutter's own `InheritedWidget` made easier. Flutter's official docs use it to teach app state management, so many developers already know it. For a small app, or one that already works on Provider, there's no urgent reason to migrate.

Its limits show as an app grows. Errors from reading a provider in the wrong place only appear at runtime. Logic tied to `BuildContext` is harder to reuse outside widgets. And async states are yours to model.

## How to choose in 30 seconds

- **A new app:** Riverpod.
- **Lots of async data from APIs:** Riverpod.
- **An existing app that works on Provider:** stay on Provider.
- **You're learning Flutter:** Provider first, as Flutter's docs teach it, then Riverpod.

## FAQ

### Is Provider deprecated?

No. Provider is still published, still used in Flutter's official docs and still works. Its author built Riverpod as the successor that fixes design limits Provider couldn't.

### Do I have to use code generation with Riverpod?

No. Code generation with `@riverpod` is recommended because it cuts boilerplate, but you can declare providers by hand.

### Can I migrate from Provider to Riverpod gradually?

Yes. Both can run in the same app. Riverpod's docs have a "From Provider" section that walks through moving one piece at a time.
