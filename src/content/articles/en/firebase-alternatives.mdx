## Why teams leave Firebase

Firebase's free Spark plan is generous, and the paid Blaze plan keeps the same free quota. The risk is how Blaze bills: per document read, write and delete. A query in a loop, or a page that reads too many documents, shows up directly on your bill.

Firebase gives you two tools. Budget alerts only send emails and don't stop anything. Spend caps can pause a service when it goes over budget, but they only exist for Cloud Functions, App Hosting, AI Logic and Extensions. Firestore isn't on the list. The other reason teams leave is lock-in. Firebase is proprietary, so you can't run it on your own servers.

## Supabase is the best way off Firestore

<ToolFacts tool="Supabase" price="Free; Pro $25/mo per organization + compute" runsOn="Cloud or self-hosted (Docker)" license="Open source (Apache 2.0)" />

Supabase is a Postgres database with auth, file storage, edge functions and realtime around it. Pro costs $25 a month per organization and includes $10 of compute credits, enough for one Micro instance. Pro has a spend cap on by default that blocks overage charges. Compute hours aren't covered by the cap, but they only grow when you pick a bigger instance.

It's also the only option here with official Firebase migration guides. They cover Auth users, Firestore collections and Storage files. Your users can keep their passwords, because Supabase's import tool takes Firebase's password hash parameters. You start by exporting users with the Firebase CLI:

```sh
firebase auth:export users.json --format=json --project your-project-id
```

Realtime listeners change shape but not idea. A Firestore `onSnapshot` on a collection becomes a channel on a table:

```js
supabase
  .channel('new-orders')
  .on('postgres_changes', { event: 'INSERT', schema: 'public', table: 'orders' }, (payload) => {
    console.log('New order:', payload.new);
  })
  .subscribe();
```

The free plan's catch: projects pause after one week of inactivity, and you can have two active ones.

## Appwrite keeps documents and adds SQL

<ToolFacts tool="Appwrite" price="Free; Pro $25/mo, +$15 per extra project" runsOn="Cloud or self-hosted (Docker)" license="Open source (BSD 3-Clause)" />

Appwrite's built-in databases use documents and collections, so the model will feel familiar coming from Firestore. Since Appwrite 2.0 you can also create native PostgreSQL or MySQL databases in a project. Those are dedicated instances that start at $10 a month, and Pro includes $10 in database credits each month.

Pro costs $25 a month and includes 2 TB of bandwidth per project. Each extra project adds $15. Free projects pause after seven days with no development activity in the console. User traffic doesn't count, and projects paused for 90 days are deleted.

## PocketBase if you want to own the server

<ToolFacts tool="PocketBase" price="Free (you pay for the server)" runsOn="Any Linux, macOS or Windows server" license="Open source (MIT)" />

PocketBase is one Go executable with an embedded SQLite database, auth, file storage, realtime subscriptions and an admin dashboard. There's no hosted plan and no per-operation billing. Your cost is the server you run it on.

You take on the work Google did for you: backups, updates and uptime. PocketBase is still before version 1.0, and its README says full backward compatibility isn't guaranteed until then.

## What I'd plan before leaving Firebase

I still use Firebase where it shines. Static sites like Musa Rosa are a Next.js export deployed with `firebase deploy --only hosting`, and I have no reason to move them. When a client wants to leave Firebase, it's almost always about Firestore costs or getting their data into SQL.

Plan the data model before you move anything. Firestore documents don't map one-to-one to tables: subcollections become tables with foreign keys, and duplicated fields become joins. I write the target schema first, migrate Auth users second, so people keep their passwords, and move data and Storage last.

And whatever you choose, set budget alerts on day one. An inefficient query in a listener loop is the most common source of surprise bills I've seen, on any platform that bills per operation.

## How to choose in 30 seconds

- **You want SQL and an official migration path:** Supabase.
- **You want to keep a document model, open source:** Appwrite.
- **You want no platform bill at all:** PocketBase.
- **Your app stays inside the daily free quota:** stay on Firebase.

## FAQ

### Can I set a hard spending limit on Firebase?

Not for Firestore. Budget alerts only send emails. Spend caps that pause a service exist for Cloud Functions, App Hosting, AI Logic and Extensions only.

### Can my users keep their passwords if I leave Firebase?

With Supabase, yes. Its Firebase Auth migration guide imports users exported with `firebase auth:export`, using Firebase's password hash parameters so existing passwords keep working.

### Is there an open-source Firebase I can self-host?

Yes. Supabase (Apache 2.0), Appwrite (BSD 3-Clause) and PocketBase (MIT) can all run on your own servers.
