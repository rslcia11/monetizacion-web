The verdict
The widget tree problem
Remi Rousselet created both Provider and Riverpod. Provider was one of the first officially endorsed state management libraries for Flutter. However, it relies heavily on BuildContext to read state. If you try to read a provider outside of its widget hierarchy, the app crashes at runtime.   

Riverpod was designed specifically to fix these flaws. It moves providers out of the widget tree entirely, making them global Dart objects. This allows you to catch errors while writing code instead of waiting for the app to crash on a user's phone.

Riverpod: safe and context-free
With Riverpod, you declare your state as global variables. Because they do not depend on Flutter's UI layer, you can use them in plain Dart applications or access them easily inside background processes.   

Riverpod catches dependency errors at compile time. You cannot accidentally request a provider that does not exist. It also lets you declare multiple providers of the same type, which is impossible in Provider without overriding. While it introduces a new mental model, its testing flexibility and automatic state cleanup make it scale better for large teams.

Provider: simple but limited
Provider is easy to learn because it feels like standard Flutter widget composition. You wrap your app in a MultiProvider and read state using context.watch or context.read. It requires very little boilerplate to get a small app running.   

However, Provider is officially in maintenance mode. It will not receive new features. Its reliance on the widget tree makes it harder to scale, and large apps often accumulate massive ChangeNotifier classes that become difficult to maintain.

How to choose in 30 seconds
You are starting a new project today: Riverpod.

You want compile-time error checking: Riverpod.

You need to test business logic without UI: Riverpod.

You are maintaining an older app: Provider.

You just want to learn the basics of Flutter state: Provider.

FAQ
Is Provider deprecated?
No. Provider is completely stable and works well. However, it is in maintenance mode. It will receive bug fixes, but active feature development has moved to Riverpod.   

Do I have to use code generation with Riverpod?
No. While code generation with @riverpod and build_runner is recommended to reduce boilerplate, you can still declare your providers manually.   

Which one is better for testing?
Riverpod is much easier to test. Because providers are plain Dart objects that do not depend on the widget tree, you can test your business logic directly without having to mock a complex UI environment.
